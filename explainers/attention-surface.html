stevengonsalvez/agents-in-a-box · ainb-tui · PR #864

Five surfaces asked “does an agent need me?”. Now one answers it.

ainb had five places that could tell you an agent was waiting: a Fleet control panel, a host Inbox, ATC lite, the notification store, and the session rows themselves. Each knew part of the truth and none reconciled with the others, so the honest answer to “who needs me right now” was “check all five, then guess”. This epic collapsed them into the sessions screen, where a waiting agent is a chip on its own row and the answer is typed in a tab beside the question. The load-bearing rule underneath it: an answer’s outcome belongs to the question it answered, never to whatever the pane happens to be showing when it lands.

What replaced what

Both producers survive; only the surfaces were removed. That matters because the daemon can be down: with no hangar daemon running at all, the local notifyd producer still raises the chip and the answer still travels the tmux send path. The recording that ships with this branch is taken with no daemon running.

How one answer travels

1
crates/ainb-core/src/fleet/attention.rs — route_answer

Every chip is routed against the session it landed on, after the producers are merged, because only the session row knows whether there is a pane to type into. Four outcomes in one place, so the chip’s grey and the ask tab’s refusal sentence can never disagree about why: not a question; a daemon row while the daemon is up; a local permission request, which goes to the approve broker and never to the pane; or the session’s own tmux pane.

2
crates/ainb-core/src/fleet/answer.rs — AskState

The outcome is keyed by request, not by the pane. The in-flight entry doubles as the double-send latch, so the view and the fact cannot disagree, and a failure carries the draft that was typed when it went out.

pub struct AskState {
    request: Option<String>,
    // What each send did, keyed by the request it was answering.
    phases: Vec<(String, AnswerPhase)>,
    // Each entry names the request it belongs to.
    inbox: Arc<Mutex<Vec<(String, AnswerPhase)>>>,
}
3
crates/ainb-core/src/fleet/control.rs — resolve_and_send_typed

The send re-resolves the target pane from the session’s identity and cwd rather than trusting a name captured when the chip was built, and refuses an ambiguous match instead of typing an answer into whichever pane the name happens to hit now. Two live sessions in one worktree is a refusal, not a coin flip.

4
crates/ainb-core/src/components/session_tabs.rs — the ask pane

All three states are visible — sending, delivered, and ✗ not answered: <reason> — because an answer that vanished into a worker with no feedback is the failure this pane exists to remove. The chip strip asks per chip whether its own answer is still on the wire, so the marker stays on the session it belongs to after the operator navigates away.

Each recording below is a real ainb tui in a real tmux session, seeded into a throwaway $HOME and read back off the pane — not a mockup, and not a screenshot of a passing test. Recordings of runs that went wrong were discarded rather than published: four takes of the answer flow, two of the broadcast, and four of the copilot, each listed below with what was wrong.

Phase 4 · answering, and being told the truth about it

The answer is typed beside the question. Two live sessions share this worktree, so the send refuses as an ambiguous target rather than typing into whichever pane the name happens to hit — and says so, keeping the operator's text. It then walks to the other waiting question, whose pane reports nothing because nobody answered it, and walks back to find the failure still on the question that produced it. That last beat is the whole invariant: an outcome belongs to its question, not to the pane.

Phase 8 · broadcast, with the checkboxes as the recipient list

The deleted Fleet panel carried its own recipient picker, which could disagree with the rows an operator had already selected. Here the checked rows are the recipients — the tab renames itself to broadcast (2) and names them — and the send reports one leg per recipient with its own outcome. A fan-out that says “sent to 2” when one was refused is the failure this replaced.

Four defects adversarial review found after the phases landed

  • The surface lied about which question failed. A single shared phase field was written by whichever send worker landed last, so answering A and moving to B painted A’s failure under B’s question, and returning to A showed nothing at all. Keying the outcome by request closed it (ba0c863b). A surface that reports the wrong question is worse than one that is silent about it.
  • A failed swap left the guardrail loosened. The copilot dial was written before the engine swap and left there when the swap failed. The client only adopts a mode from an applied outcome, so a configure that loosened to yolo and then failed armed it underneath a header still reading guarded — destructive tools reaching auto with no confirm card. A failed configure now changes nothing, in either direction (17ee6a6b).
  • The auto-continue gate could be armed by a branch name. The sweep scanned the whole stored event, and the event carries the session’s own cwd. The patterns are word-boundary matches and both - and / are non-word characters, so a worktree called econnreset-repro matched on its path — which is exactly what someone debugging this class of failure calls a branch. It now reads one named field (d5735835).
  • Every ACP task run was refused. Unifying the adapter registry pointed every mint at the chat list, which deliberately hides #task: keys so no chat caller can reach a task’s sandboxed process — but the task executor mints against exactly such a key. Tasks died as spawn_error with no delivery legs, and the task’s pinned permission mode was lost with it. One scope-aware lookup answers both (8e779d3c).

Known, and deliberately left open

  • The cancel’s version check is vacuous. The cancel re-reads the snapshot immediately before writing it, which removes the staleness property optimistic concurrency exists for. The page now retires a delivery leg past the turn deadline, so the exposure is one deadline rather than the life of the pane; closing it needs the version the leg was created at (dd9a5139).
  • The sweep is Claude-hook-only. A wire session’s error event type is the raw method, none of which is in the allowlist, so Codex and ACP sessions always land in skipped_opaque. That fails closed, which is the right direction for a gate that types at an unattended agent; widening what auto-continue reaches is a behaviour change that needs its own verification rather than a longer list.

Recordings that were made and thrown away

  • Answer, take 1. The seeded onboarding version was a hardcoded 0.0.0, so the TUI ran its setup wizard and the tape drove that instead of the sessions screen.
  • Answer, take 2. Two Tabs from preview lands on thread, so the answer was typed into the thread composer rather than the ask pane.
  • Answer, take 3. Down never moved the session: thread and copilot own composers that swallow the arrows. The walk now routes through log, which does not.
  • Answer, take 4. The walk moved one row, which is the other session on the same worktree — the same question, so correctly the same outcome, but not the thing being shown.
  • Broadcast, take 1. Run without a daemon, so the send refused for want of one. Correct behaviour, and the pane said so and kept the text — but it does not show the verb working, and broadcast is daemon-owned.
  • Broadcast, take 2. The daemon's bring-up pushed the whole tape out of step, so keys landed before the screen was ready and fired as session shortcuts instead — one of them starred a workspace. The daemon-backed tapes now wait far longer before the first keystroke.
  • Copilot, four takes. With a daemon attached the pane stopped taking the tab-strip keys, and every take ended on preview rather than the copilot tab. Longer settles, a re-based key prefix and a proven Tab sequence all failed the same way. Abandoned rather than published mislabelled.
