The ainb chat bus: built, proven, recorded

TL;DR ainb can now hold a conversation. Messages go to running tmux sessions AND to headless ACP agents through one bus, with receipts per recipient, live execution transcripts, actionable permission prompts, and resume across a daemon crash. Part 2 gives the fleet a voice: a #copilot channel whose agent holds fleet-control tools behind a confirm-card guardrail that now actually blocks on the operator, per-session chat threads, broadcast channels with a reason on every leg, and both the TUI and the macOS app operating the same wire. Part 1 is six phases, five merged PRs, sixteen named invariants. Part 2 is not yet merged (PR #662, base main). Eleven live journeys are recorded end to end; two of them, unlike the first nine, drive the real TUI binary rather than only the daemon and the CLI. Every recording below is an uncut run, and every frame was read to confirm it shows the assertion it claims.

What shipped

The port took the good ideas from block/buzz (agents as first-class chat members, a clean timeline with execution detail on a side channel) and put them on ainb's own daemon rather than adopting buzz's Nostr relay stack.

How it works

every client speaks ONE wire contract; one process owns the store

+----------+  +----------+  +----------+   fleet/* JSON-RPC over hangar.sock (v2)
| ainb TUI |  | macOS    |  | ainb CLI |   msg send . msg list . msg follow
| plugin   |  | Fleet    |  | + web    |   acp create . transcript [--follow]
+----+-----+  +----+-----+  +----+-----+
     +-------------+-------------+
                   v
+----------------------------------------------------------+
| hangar daemon                                            |
|  fleet_message (seq = commit order) - receipts per leg   |
|                                                          |
|  +-- tmux leg --------+   +-- ACP leg -----------------+   |
|  | verified send-keys |   | one process per provider,  |   |
|  | (unchanged)        |   | many sessions multiplexed  |   |
|  +--------+-----------+   +---+--------------+---------+   |
|           v                   | stdio        |             |
|    your tmux panes    +-------v------+ +-----v--------+    |
|                       |claude-agent- | | codex-acp    |    |
|                       |acp           | |              |    |
|                       +--------------+ +--------------+    |
|                                                            |
|  timeline    <- final message only                         |
|  transcript  <- every chunk: thought, tool call, plan, cost|
|  permission  <- attention row, answered over fleet/action  |
+------------------------------------------------------------+
*
The idea worth stealing from buzz: the chat timeline only ever gets the agent's final message. Thinking, tool calls, plans and token cost stream to a separate transcript. Your chat view stays readable and never has to render half-finished markdown.

Part 2: the guardrail is live

Part 2 puts an agent behind a #copilot channel, holding an MCP tool table that can read the whole fleet, send messages as itself, and reach the destructive tools (kill, spawn, interrupt, archive) behind a confirm card. Every tool call goes through one gate before it can run anything.

tool call -> classify -> Auto/Refused/Confirm, and Confirm BLOCKS on a human

  model    tools/call     +------------------------+
  (tool +  ---------->    | fleet/copilot_gate     |   one classifier, daemon-side
  args,                   | Auto ------------------|-> run
  never                   | Refused ----------------|-> never runs
  prose)                  | Confirm -> card (open) -|-> fleet/confirm_event
                          +------------------------+          |
                                                          operator answers
                                                       approve / edit / deny
                                                                |
                                                        Run (gate's own args)
                                                          / Denied / Expired
*
The review found it was not enforced. copilot::gate minted confirm cards and was fully tested, but nothing on the production path called it: the tool server answered a Confirm verdict with a structured error straight back to the model, so the entire approve surface, TUI cards, confirm_list, confirm_answer, the CLI verbs, was reachable only by cards nothing minted. fleet/copilot_gate now parks a real card and the tool call blocks on the operator's answer, bounded by a TTL strictly shorter than part 1's 30-minute turn deadline (a card that outlived the deadline would get its turn converged out from under a dialog the operator is still looking at).

The tool arguments are projected onto the tool's own declared schema keys before the card is persisted, so a model-authored justification or operator_approved key never reaches the human's approve dialog. There is one classifier, not two: the tool server's own live Guardrail copy was deleted, because a second copy of the rule, running downstream of every transcript the copilot has read, is the easier one to soften. The server now asks the daemon and executes only on Run, using the gate's own arguments, so an operator who edits a card edits what actually runs.

The proof

Every recording is one uncut run of ainb-tui/scripts/chat-bus-smoke.sh. Each run builds a scratch world: its own hangar home, a real daemon, the real ainb binary, three real tmux sessions, and an ACP adapter. Frames were extracted from every tape and read; the assertion text quoted under each recording is text that was actually on screen.

What is real and what is not, precisely. The daemon, the store, the CLI, the tmux sessions and the protocol traffic are real: these runs speak the same wire the TUI and the macOS app speak. The ACP agent on the far end is a scripted fixture that implements the protocol, not a live Claude or Codex process, because no adapter is installed on this machine. Every tape says so in its own banner (adapter mode: fixture). The adapters themselves were measured by hand against the real thing when the protocol behaviour was pinned, and the real-adapter tests are written and skip until an adapter is present.

The fault matrix

Five more journeys, each provoking a specific failure and asserting the system's answer.

The operating surface

j1 through j5e drive the daemon and the CLI. Part 1 shipped a chat bus the TUI consumes without anything ever opening the TUI, and that is exactly how a real bug got past every recording above: the Fleet panel rendered an ACP session's provider as UNKNOWN while every daemon-level and CLI-level test stayed green. j6 and j7 close that gap: each additionally cold-launches the real ainb tui on a private tmux server and operates it with the keys an operator would press. That distinction is the whole point of both.

What the reviews caught

Every phase was built by one agent, reviewed adversarially by another, then reviewed again before merge. That third pass is where the expensive bugs died, each one found by reading the code rather than by a failing test.

A message stream that silently dropped rows phase 1

The cursor was a daemon-minted ULID, generated before the write transaction. Two concurrent sends could commit out of id order, and a subscriber that had already paged past the higher id would never see the lower one. No error, no gap, just a missing message. Replaced with a SQLite-assigned sequence so cursor order is commit order, with a concurrency test written to fail against the old design.

An older permission that could never be answered phase 5

With two permissions parked at once, the newer one overwrote the session's request fingerprint, so answering the older ask was refused before the pool was ever consulted. The adapter stayed blocked until the deadline. Reproduced first with a two-ask fixture, capturing the exact refusal, then fixed by making the parked map authoritative.

Whole turns lost when an adapter exited phase 5

Buffered transcript notifications were dropped at three points on the exit path, and because the upstream notification future outlives the supervisor loop it could lose an entire turn, not just the tail. The supervisor now drains to silence and the actor flushes its reducer before detaching.

A prune that deleted more than it exported phase 6

The retention command exported a snapshot, then deleted by re-evaluating the operator's watermark. Anything committed in between was destroyed with no export and no error. The delete now takes the exported watermark, so export-then-delete is total by construction.

Resume that would have quietly degraded on Claude gate

Re-running the protocol probes against fresh adapter versions found that mode-loss-on-load affects both adapters, not just Codex as the original spike recorded. Had the plan's Codex-only re-apply shipped, every Claude resume would have failed its mode assertion and silently fallen back to re-priming, never using session/load at all. The j3 recording above is the proof it takes the fast path.

Part 2's highest-value findings were all caught by adversarial review, not by a failing test: the code did exactly what it was asked to do, and what it was asked to do was wrong.

A copilot write that could wear the operator's name part 2, wave 1

Every message persisted sender: "operator", so a copilot's message was indistinguishable from a human's at every surface that renders one, including the receiving agent's re-prime corpus. That routes around the entire guardrail table: a copilot never needs the kill tool if it can ask another agent to do it while wearing the operator's name. message_send now takes an optional actor and refuses a blank one; absent still means the operator, so every existing caller is unchanged.

A guardrail that was fully tested and unreachable part 2, gate

copilot::gate classified tool calls and minted confirm cards correctly, but nothing on the production path called it: the tool server answered a Confirm verdict with a structured error straight back to the model, so the entire approve surface, TUI cards, confirm_list, confirm_answer, the CLI verbs, had no producer that could ever reach it. fleet/copilot_gate now parks a real card on the live path and the tool call blocks on it.

The copilot held the daemon's own global credential part 2, gate

The whole boundary rested on "the copilot only acts through its MCP tool table", and nothing enforced it: anything holding the daemon's token could call the same methods directly, including answering its own confirm cards. Authorization is now per connection: a Caller is either the operator (the daemon's own token) or the copilot (a token minted per channel scope, restricted to the read methods, the gate, and the two writes the tool table can reach after the gate says run). Same shape as the sender: "operator" finding: a guarantee asserted in the design and absent from the code.

An injection test that proved less than it claimed part 2, gate

The adversarial test now makes the model obey the injected instruction verbatim, exactly as a compromised model would, both demanded tool calls issued with the injection's own prose as justification, then asserts nothing reached an execution path: no message row, no write on the socket, one denied activity row per attempt. Proving the copilot declines is not the same claim as proving obedience is harmless, and only the second one holds up against a model that does not decline.

Two races in the confirm-card path part 2, gate

An edited confirm answer was projected but not re-classified, so an edit that dropped a required key, like answer from an answer_need, could run with a default that silently resolved another agent's open need. It is now re-classified after projection, and a shape-invalid edit is refused rather than run. Separately, the card row could be persisted before its waiter was registered, so an answer landing in that window would resolve the durable row to approved, find no waiter, and leave the tool call to time out: a card reading APPROVED everywhere while the tool itself resolved EXPIRED. The waiter now registers first.

A chat pane that pre-armed an approval part 2, macOS

The confirm section adopted the first open card on the first poll, so an operator who pressed Approve without reading the row could approve whichever card happened to arrive first, not the one they meant to answer. Every open card now renders its own row with its own Approve, Deny and Edit controls; nothing is pre-selected.

What is next

Part 1 gave the fleet a nervous system. Part 2 gives it a voice, and what shipped above is real: the guardrail blocks on the operator on the live path, threads and broadcast channels work, and both operator surfaces render a copilot message and an operator message as visibly distinguishable. What is left, stated as plainly as the rest of this page:

The macOS pane has not been built by its own author. There is no Swift toolchain on the machine PR #662 was written on, so no Swift test in that change has been executed by the person who wrote it. fleet-macos-contract.yml is what proves it, and the PR should not merge until that job is green.

PR #662 is not merged. Everything in this section (the live guardrail, threads, channels, both surfaces, j6 and j7) is on fix/tui-tripwire-hangar-home against main, reviewed, not yet in main itself.

A DELIVERED leg is not proven end to end. It needs a live agent pane, and no agent runs in a tripwire. The mixed delivered/rejected rendering is pinned in unit and CLI tests where it can be driven deterministically, which is not the same claim as a message actually reaching a live process.

No real ACP adapter has ever run in CI or in any recording on this page. Every ACP run, part 1's j2 through j4 and part 2's j6 and j7, uses the fake_acp_adapter fixture. The real-adapter tests exist and skip until an adapter is installed; the adapters were measured by hand against the real thing when their protocol behaviour was pinned, but that measurement is not itself in this page's proof.

The guardrail's operator-named-sessions state is not wired to a live turn yet. fleet/copilot_gate currently builds an empty Guardrail for every call, which is the fail-closed value, not a finished feature: every answer_need takes a confirm card regardless of which sessions the operator's own message named, because nothing yet computes that pinned set from the turn that triggered the call.
