# Hangar P1 — Daemon + task FSM (Weeks 3-4)

**Phase:** P1 · **Beads:** `hangar:P1.1` → `hangar:P1.7` · **Loop:** per-bead TDD+review (`per_bead_tdd_review_loop_shape`)

## Goal

`ainb-hangar-daemon` claims a queued task, dispatches it, starts it, runs ONE provider (claude) end-to-end as a subprocess in an isolated env, and finalizes idempotently. Full Multica FSM verbatim: `queued → dispatched → running → done|failed|cancelled` + TTL sweepers (queued 2h, dispatched 5min, running 2.5h) + 90s reclaim window for stale `dispatched` + idempotent finalize (0-row UPDATE → re-read → success if terminal) + retry rows via `parent_task_id`.

**Builds on:** P0 — schema, migrations, sqlx pool, `HangarClock` trait, ulid injection, isolated `$HOME` tempdir per test.

**Blocks:** P2 (beads sync needs claim semantics) + P3 (plugin caps dial daemon).

**Out of scope:** TUI integration (P3/P4), transport surface (P3), beads sync (P2), other providers (codex/copilot — P5+), cron scheduler (P7), GitHub `gh` integration (P9).

## Acceptance

- [ ] `ainb-hangar-daemon` boots, claims one queued task, transitions through all four happy states (queued → dispatched → running → done) against a real SQLite WAL DB
- [ ] One retry chain proven: a `failed`/`runtime_offline` task spawns a child row with `parent_task_id = old.id`, attempt counter +1
- [ ] Tripwires (≥2):
  - `tripwire_task_happy_path_claude_provider.rs` — spawns daemon, enqueues task, daemon claims+executes `echo "ok"` proxy as fake claude provider, terminal state = `done`, `result.session_id` populated
  - `tripwire_ttl_sweeper_fails_stale_dispatched.rs` — enqueue, claim (no start), advance HangarClock past 5min, sweeper fails task with `failure_reason='timeout'`
- [ ] `cargo test --workspace` green
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` clean
- [ ] `hangar:P1` bead closed + PR merged (no force-push, no squash per `feedback_merge_commit`)
- [ ] User-visible proof: asciinema or screenshot in PR body showing `ainb-hangar-daemon` log + `sqlite3 ~/.ainb/hangar.db "SELECT id, status, attempt, parent_task_id FROM agent_task_queue"` showing FSM walk + retry row

**Crate:** `ainb-tui/crates/ainb-hangar-daemon/src/sweeper.rs`

### RED

  - `queued_ttl_2h_fails_task` — insert queued, advance clock +2h+1s, run `sweep_expired_queued(&pool, &clock)`, assert: status=`failed`, `failure_reason=timeout`. Threshold `Duration::from_secs(7200)` named `QUEUED_TTL` (cite `runtime_sweeper.go:52`).
  - `queued_under_ttl_untouched` — advance +1h59m, sweeper runs, no change
  - `dispatched_ttl_5min_fails_task` — insert dispatched, advance +5min+1s, `sweep_stale_dispatched`, asserts fail. Threshold `DISPATCHED_TTL = Duration::from_secs(300)`.
  - `dispatched_within_90s_reclaimed_not_failed` — insert dispatched 80s ago, run `reclaim_stale_dispatched`, asserts: status=`queued` again, attempt unchanged, NO fail. **This is the key Multica invariant** (`task.go:85` — 90s window for lost claim responses). Cite in test.
  - `dispatched_91s_through_5min_neither_reclaimed_nor_failed` — gap between reclaim window (90s) and dispatch TTL (5min): task stays dispatched, both sweepers skip
  - `running_ttl_2_5h_fails_task` — `RUNNING_TTL = Duration::from_secs(9000)`. Cite `runtime_sweeper.go:40`.
  - `sweeper_batch_caps_at_500` — insert 600 expired queued, run once, assert 500 failed in this pass, next pass takes the rest. Matches Multica batch behaviour, prevents long sweep transactions.
  - `sweeper_idempotent_on_already_terminal_rows` — task already `done`, sweeper does not flip back

### GREEN

- Three async sweeper tasks spawned by daemon's tokio runtime:
  - `sweep_expired_queued(pool, clock)` — every 60s
  - `sweep_stale_dispatched(pool, clock)` — every 30s (also runs reclaim within same query: WHERE dispatched_at < now - 90s AND dispatched_at >= now - 300s → queued; WHERE dispatched_at < now - 300s → failed)
  - `sweep_stale_running(pool, clock)` — every 60s
- `SweeperConfig { queued_ttl, dispatched_ttl, reclaim_window, running_ttl, sweep_interval, batch_size }` — configurable for tests, sensible Multica defaults in prod
- `tokio::select!` on shutdown signal so daemon exits cleanly

### REFACTOR

- Sweepers share `Sweeper` trait; daemon's main loop registers a `Vec<Box<dyn Sweeper>>` via dyn-dispatch
- Metrics: `hangar_sweeper_swept_total{kind="queued|dispatched|running",outcome="failed|reclaimed"}` counter

**Acceptance:** Sweeper tests deterministic — zero `tokio::time::sleep` in tests, all clock-driven. Cite three Multica source-line references.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| SQLite WAL write contention under concurrent claim by multiple runtimes (multi-daemon, deferred to P5 but DB must handle) | Med | Single-writer task pattern; benchmark in P1.2; document `--test-threads` ceiling |
| `git worktree add` slow on cold cache | Low | Reuse from existing `ainb-core` worktree helpers per build-plan §reuse-map; do not rebuild |
| Tripwire flake on slow CI from tmux capture-pane timing | Med | Substring poll with 30s budget; raise to 60s on CI via env override; do NOT use full snapshots (`reference_self_paced_loop_swarm_babysitter`) |
| `HangarClock` injection forgotten in one sweeper → real-time leak in tests | Med | Lint rule: no `std::time::SystemTime::now()` or `chrono::Utc::now()` outside `HangarClock` impl; clippy `disallowed_methods` config |
| Idempotent finalize wrong when concurrent COMPLETE + CANCEL: which wins? | High | Test explicitly (`finalize_concurrent_complete_vs_cancel`); document: first transactional UPDATE wins, loser re-reads and returns `AlreadyTerminal` if same target, `TerminalMismatch` otherwise. Same as Multica's behaviour. |
| Fake-claude script Unix-only → Windows CI breaks | Low | Hangar is Unix-only per `reference_rust_unix_only_apis` + locked v1.0 decision; skip Windows in matrix |
