─ WHAT D4-PRIME MAY NOT REOPEN ─

· D17's bump rule and its one integer (`protocol.rs:16-28`). Nothing in this node branches on `daemon_version` (`auth.rs:146-147`); a reader that needs a method asks `HelloResult::advertises`. The version string is shown to the operator and compared to nothing.
· A release build takes its daemon from beside its own executable and from nowhere else (`main.rs:284-287`). The updater does not add a path, an environment variable or a `PATH` lookup for the daemon; the cure for a stale sidecar is a newer bundle.
· The sidecar never kills a daemon on the app's exit and never spawns a second (`sidecar.rs:17-19`, multi-surface `:267`), and this node adds no daemon lifecycle action of any kind. The locked row asks for a banner that names the fix; the app draws the banner and the operator runs the verb. A pid read from `daemon.lock` (`sidecar.rs:481-487`) is never a target for a signal from this app: pids are reused, and the daemon that holds the lock is usually the terminal's flock winner serving live sessions.
· A release bundle carries no WebDriver and binds no port (`desktop.yml:224-324`, `main.rs:358-365`). Every bundle the release job produces goes through the same smoke, not only the binary.
· The pinned public key (`update.rs:18`), the manifest's file names (`:340-341`) and the meaning of `assets[]`. **No desktop archive ever goes into `assets[]`**: `asset_for_current_platform` (`:82-88`) matches on `target` alone and takes the first hit, so a 1.28.2 CLI in the field, which has no notion of a product, would download a `.dmg` and install it as the `ainb` binary. Desktop bundles live under a new top-level `desktop` key that `ReleaseManifest` (`:24-30`, no `deny_unknown_fields`) ignores as it stands, one signature still covers the whole file, and a test decodes the new manifest through the 1.28.2 struct shape and asserts it picks its own asset. `update_domain.rs` stays green unchanged.
· No path skips a verification step. No feature, flag, environment variable, setting, channel or debug build makes the updater download from another host, accept another key, or apply a bundle that did not pass every check in D4c's list in order. The throwaway-key seam, `verify_manifest_with_key` (`update.rs:97-101`), and the local-listener seam are reached from the desktop under `cfg(test)` only, and a `compile_error!` shaped like `main.rs:358-365` refuses a release build that carries any test seam of the updater. The trust root before a swap is the manifest's signature plus the archive's sha256, stated as such; no `spctl` or `codesign` verification runs on the extracted bundle, and D4·spec says so out loud so nobody later assumes it did.
· Secrets are named, never minted. The Apple identity, the notarisation credential and the team are #530's, supplied by the human as repository secrets; the lane writes the steps that read them and the gate that says when they are absent. No signing is ever attempted with an identity that is not this product's (#530's last line).
· One version per release (`release-process.md:18-20`). The desktop joins that version; it does not keep `0.1.0` or a line of its own.
· Locked decisions D10 to D18 stand; the host switcher and every transport question are R1's (amendment 26). `ainb-tui/crates/ainb-core/src/app/*` is untouched, the standing lane rule.

The first seam is the one the multi-surface spec wrote a row for (`:267`) and nobody built. Today a daemon from a newer `ainb` that refuses the desktop's range is answered by a spawn: the child loses the flock, exits 0, and the supervisor polls hello for three minutes against a daemon that keeps saying "restart from the newer binary" before it degrades with "no daemon answered", which is the wrong sentence. After D4a the refusal is read on the first frame, nothing is spawned, and the banner says which of the two binaries to move. The fourth seam is where the node's size is: the CLI's updater owns the network, the key and the verify, and the desktop owns only what differs, the target rows it looks for and the swap of a bundle rather than a file.

The skew table this node has to make true, with the desktop at version D and the daemon that owns the home at version M:

| daemon that owns the home | today | after D4a |
|---|---|---|
| none | the bundled daemon is spawned | same |
| older than D, ranges overlap | hello negotiates the highest common version; readers take their older path by capability | same; the daemons panel shows `M`, the range, and "this bundle carries a newer daemon" with the stop verb named |
| older than D, no overlap | spawn, child loses the flock, 180 s of polling, `Degraded { "no daemon answered" }` | `Incompatible` on the first frame, no spawn, banner names both ranges and the same verb |
| newer than D, ranges overlap | negotiates down; the newer daemon serves | same; the panel says the daemon is newer than this app, and the update check runs at once |
| newer than D, no overlap | as the third row | `Incompatible`, no spawn, banner says "this app is older than the daemon; update the app", the update check runs at once |

No row offers a restart from the app. The banner in the second, third and fifth rows names the binary to move and the verb: the daemon's own stop verb, `ainb daemon <daemon> stop` as the executor already spells it (`executor.rs:217-226`), run from a terminal by the operator, after which the banner's "retry" (`main.rs:280-282`) probes again and the bundled daemon is spawned into the free home; or an update of this app, when the daemon is the newer one. The desktop's daemon verbs run through the `ainb` on `PATH`, a third version, which is one more reason the app does not act on its own: the panel shows all three versions and the operator chooses.

─ THE HUMAN-DRIVER RUN, WHAT THE HUMAN RUNS ─

The gate "release-branch human-driver run" is a human step and stays one.
