# Research: Can the read-only tmux preview pane become a live, attachable in-place tmux pane?

**Date**: 2026-06-02 11:07:19
**Repository**: agents-in-a-box (ainb-tui)
**Branch**: feat/tmux-in-pane
**Commit**: 526655fd674ef9099f61d506cb8fed807332811f
**Research Type**: Comprehensive (codebase + web prior-art)

## Research Question

Can the ainb TUI "preview pane" (currently read-only) become the *actual* live tmux
pane that the user can attach into and interact with directly — eliminating the
current "attach → make changes → detach" full-screen round-trip? And what product
repositories have already implemented embedding a live/interactive terminal or tmux
session inside a TUI pane?

## Executive Summary

Yes — it is feasible, and the ingredients are already in `Cargo.toml`. The pragmatic
path is to **embed a PTY running `tmux attach` directly inside the ratatui pane**,
parse its output with a VT100 emulator, render it as a terminal-cell widget, and
forward keystrokes back to the PTY when the pane is focused. This is the exact
pattern `tui-term` (vt100 + portable-pty + ratatui) implements, and it is what
amux (Go), mprocs, and Ratty already ship. The heavier alternative — tmux **control
mode (`-CC`)**, as used by iTerm2/Ghostty — gives per-pane structured output and
native layout awareness, but is overkill because ainb runs one agent per single-pane
tmux session (no multi-pane layout to manage).

The single most important integration constraint: **`tui-term` latest (0.3.4) targets
a newer dependency set than ainb pins** — it requires `portable-pty ^0.9`, `vt100
^0.16.2`, and the split `ratatui-core ^0.1` / `ratatui-widgets ^0.3` crates, whereas
ainb is on `portable-pty 0.8`, `vt100 0.15` (dev-only), and `ratatui 0.26`. So either
upgrade the deps, pin an older `tui-term`, or (cleanest) vendor the small
`PseudoTerminal` widget and keep current pins.

## Key Findings

- **Current preview is read-only by construction**: a 5-second poll of
  `tmux capture-pane -p -e -J` → `Option<String>` on the model → ANSI-parsed into a
  static ratatui `Paragraph`. There is no input path into it.
- **Current "attach" is a full-screen takeover**: `attach_handler` disables raw mode,
  leaves the alternate screen, and `tmux attach-session` inherits the real stdio; the
  TUI is frozen until the user hits `Ctrl+B D`. The code comment at
  `tmux/session.rs:185` explicitly says they avoided "proxy through a PTY" because the
  exec route was "simpler and more reliable."
- **The ingredients for the embed are already present** but dead at runtime:
  `portable-pty 0.8` is a dependency, `PtyWrapper` exists but is only ever set to
  `None` in the live path, and `vt100 0.15` is a dev-only dependency used in tests.
- **Prior art exists at every point on the spectrum**, and the empty niche is exactly
  what `feat/tmux-in-pane` would fill: *a Rust/ratatui agent-orchestration TUI with a
  truly interactive in-place pane*. claude-squad (the closest competitor) does **not**
  do this — it does capture-pane preview + handoff attach, same as ainb today.
- **Three architectural approaches**, in increasing complexity: (1) poll
  `capture-pane` (read-only, today), (2) embed a PTY running `tmux attach` + VT
  emulator (interactive, recommended), (3) tmux control-mode `-CC` client
  (structured, multi-pane-aware, heavy).

### The three approaches (prior-art comparison)

```
 (1) capture-pane poll        (2) embed PTY + VT emu        (3) control mode -CC
 ────────────────────         ──────────────────────        ────────────────────
 tmux capture-pane ─poll─▶    PTY[ tmux attach ] ─bytes─▶    tmux -CC ─%output─▶
   String ─▶ Paragraph          vt100::Parser ─▶ Screen        per-pane VT emu
   READ-ONLY                    PseudoTerminal widget          + %layout-change
   ainb TODAY                   keys ─▶ PTY master write        native layout tree
   claude-squad                 INTERACTIVE IN-PLACE           iTerm2 / Ghostty
                                amux / mprocs / Ratty          (multi-pane; heavy)
```

| Dimension          | (1) capture-poll      | (2) PTY-embed (rec.)     | (3) control mode `-CC`     |
|--------------------|-----------------------|--------------------------|----------------------------|
| Interactivity      | read-only             | full (focused pane)      | full (send-keys per pane)  |
| Output latency     | pull, ~5s here        | push, instant            | push, instant              |
| Pane awareness     | per call (target id)  | one tmux client = blob   | per-pane ids + layout      |
| VT rendering work  | none (text dump)      | you emulate 1 screen     | you emulate N screens      |
| Multi-pane         | n/a                   | tmux handles internally  | host composes layout       |
| Session persists   | yes (tmux owns)       | yes (tmux owns)          | yes (tmux owns)            |
| Protocol effort    | trivial               | small (vt100 + writes)   | high (stream parser ~300L) |
| Best fit for ainb  | today                 | **YES**                  | overkill (single pane)     |

Why (2) over (3) for ainb: each agent runs in its **own single-pane tmux session**
(`tmux/session.rs:108-122`, `new-session -d -s <name> ... <program>`). There is no
multi-pane layout to negotiate, so control mode's main advantage (`%layout-change`,
per-pane `%output` routing) buys little while costing a full protocol parser. Embedding
one tmux *client* in a PTY keeps tmux's session persistence (detach/reattach survives
ainb restart) while making the pane live in-place.

### Canonical interactive pattern (verified, from tui-term `smux.rs`)

```
┌──────────────┐  try_clone_reader  ┌──────────────┐  .screen()  ┌───────────────────┐
│ portable-pty │───────bytes───────▶│ vt100::Parser│────────────▶│ PseudoTerminal    │
│ openpty +    │                    │ .process()   │             │ widget (ratatui)  │
│ tmux attach  │◀──take_writer──────│              │             │ render(area,buf)  │
└──────────────┘   key bytes        └──────────────┘             └───────────────────┘
        ▲                                                                 │
        └──── crossterm KeyEvent → byte-encode → master.write_all() ◀─────┘ (when focused)
```

- **Input forwarding**: map `KeyEvent` → bytes (e.g. arrows → `ESC [ A/B/C/D`,
  Ctrl-letter → control byte, Enter → `\n`). `tui-term`'s `smux.rs` ships the full
  mapping table verbatim.
- **Resize**: derive `rows/cols` from the pane `Rect` (minus borders); call BOTH
  `screen_mut().set_size()` (vt100) AND `master.resize()` (kernel winsize → SIGWINCH).
  ainb's `Event::Resize` currently only does `terminal.clear()` (`main.rs:539-544`),
  and `PtyWrapper::resize` exists but is never called.
- **Perf** (matters — Claude Code emits high-rate bursts): render only on a dirty
  flag set by the PTY reader; debounce repaints to a ~4–8 ms window; the 8 KB read
  buffer naturally batches bursts into single `process()` calls. ratatui's per-frame
  full-buffer diff is the real cost, so do not redraw on every byte.

**Closest competitor — claude-squad**: same product category and stack tier
(Go/Bubbletea + tmux + git worktrees). Its preview is `tmux capture-pane -p -e -J`
polled every 100 ms into a Lipgloss viewport (raw ANSI passthrough, no VT emulation) —
**the same read-only approach as ainb**. Its "attach" wraps `tmux attach-session` in a
PTY (`creack/pty`) and bridges stdio via goroutines, with `Ctrl+Q` → detach → resume.
So claude-squad is *not* interactive-in-place either — it has the identical gap ainb
has. (Attach plumbing detail is from a source read; treat exact file layout as likely,
not independently re-verified here.)

**amux** is the strongest direct analog for the target UX: a Bubbletea TUI that runs a
**live PTY reader inside the pane** (`creack/pty` + VT-mode-aware capture), so the pane
*is* the running session without leaving the TUI. The Rust equivalent of amux's
approach is precisely `portable-pty` + `vt100` + `tui-term` → ratatui widget.

**Reference architecture (Rust, best-in-class)**: **Zellij** — PTY thread → `vte`
crate parser (`Grid: vte::Perform`) → custom cell grid → render to all clients;
`PtyWriter` thread owns master fd for input. Heavier than needed, but the canonical
Rust pipeline. **dvtm + abduco** (C) is the minimal classic separation: dvtm owns
VT-parse+grid+render, abduco owns only attach/detach over a Unix socket.

**Control-mode reference**: iTerm2 (`tmux -CC`, production since ~2013) and Ghostty
(Zig, in progress for 1.4) are the mature `-CC` clients. Protocol = line-based over
stdio: `%begin/%end/%error` command blocks + async `%output %<pane> <octal-escaped>`,
`%layout-change`, `%window-add/close`. Rust crates (`tmux_interface`, `tmux-lib`) only
wrap the CLI / parse layout strings — **no crate implements the full `-CC` stream
parser**, so approach (3) means writing ~300 lines of stream parser yourself.

### The dependency-version constraint (verified on crates.io)

```
 tui-term 0.3.4 (latest) requires        ainb-tui pins today
 ─────────────────────────────────       ──────────────────────
 portable-pty  ^0.9.0   (optional)        portable-pty  0.8   (dep, unused)

 ratatui-core  ^0.1.0                      ratatui       0.26  (single crate)
 ratatui-widgets ^0.3.0
```

The gap is bigger than just vt100/portable-pty: tui-term 0.3.4 moved to the split
`ratatui-core`/`ratatui-widgets` crates (≈ratatui 0.30 era). ainb is on the older
single `ratatui 0.26`. `vt100 0.16` also has breaking changes (e.g. `set_size` moved
from `Parser` to `Screen`; `Cell` lost `Default`).

## Recommendations

1. **Pursue approach (2): embed a PTY running `tmux attach` in the 60% pane**, parsed
   by `vt100` and rendered as a terminal-cell widget. Keep tmux as the session owner so
   detach/reattach still survives ainb restarts.
2. **Resolve the version conflict by vendoring the widget** (lowest risk): the
   `PseudoTerminal` cell-walk is small — copy it as a private module and keep
   `ratatui 0.26` + current pins, promoting `vt100` from dev-only to a real dependency.
   Alternatives: (a) pin an older `tui-term` that targets ratatui 0.26, or (b) do the
   full upgrade to ratatui 0.30 + vt100 0.16 + portable-pty 0.9 (larger blast radius).
3. **Add a focus model**, since interactive keys must go to the PTY: a
   `FocusedPane::Preview` state grabbed by `a`/Enter and released by a dedicated key
   (mirror claude-squad/amux's `Ctrl+Q`), so the TUI's own `j/k`/navigation keys are
   not swallowed. Repurpose the existing no-op `DetachTmuxSession` as the
   "release focus" handler; the full-screen `[ATTACHED]` notice
   (`tmux_preview.rs:268-307`) becomes unnecessary.
4. **Wire resize + perf**: compute pane cell size from the `Rect`, call
   `master.resize()` + vt100 `set_size()`; gate redraws behind a dirty flag set by the
   PTY reader with a ~4–8 ms debounce; enable bracketed paste / keyboard-enhancement on
   crossterm so complex keys pass through.
5. **Skip control mode `-CC`** unless ainb later wants multi-pane tmux layouts mirrored
   in the TUI. For the single-pane-per-agent model it is unjustified complexity.

## Open Questions

- Should the embed run `tmux attach` (preserve persistence, recommended) or run the
  agent directly in a PTY (simpler, loses tmux persistence)? Recommendation: tmux
  attach.
- Upgrade ratatui 0.26 → 0.30 now, or vendor the widget to stay on 0.26? Vendoring is
  the lower-risk first step; a ratatui upgrade is a separate, larger workstream.
- How to handle multiple selected/visible previews — only the focused pane needs a live
  PTY; non-focused ones can stay on cheap capture-pane status polling to bound resource
  use.
- Verify honeymux's exact mechanism (the control-mode-via-libghostty-vt detail reported
  by web research is unconfirmed; the repo is real but is TypeScript/OpenTUI, not the
  "Rust+Zig" originally reported).
